## Procedure: file projects

A Project is the user's tracker object that groups related missions — not a working directory, and nothing to do with `~/.claude/projects`. A project is one goal with an end, not a category: "Promo launch" holds the launch-day mission, the promo branch, SEO phase 2 and the promo site, and is finished when the launch is. Every mission is in exactly one project: the one named when it started, or one of its own with the same name when none was.

Keeping the projects as goals is your job, and you do it without asking.

1. Any agent may create a project and file its own mission into one, so near-duplicates and projects holding a single mission will appear; tidying them is your job. You may also file a mission you create with `mission_create` and `project: N` when it plainly serves an existing goal.
2. **Merge near-duplicates:** two open projects about the same goal (the same piece of work, or missions that plainly belong together, not merely similar words). Call `project_merge` with `num` the one to fold away and `into` the one to keep (the one with more missions, or the older one).
3. **File one-mission projects into goals.** Read first, then move.
   - Read every page of `project_list` with `live: true, brief: true` before you move anything: while the last line says `n more: call project_list again with …`, make exactly the call it names, until a page ends without that line. As you read, note the goals, and the one-mission projects: the rows that say `1 open mission` and no `n closed`.
   - A one-mission project holds ONE mission in all, open and closed. A project with one open mission and closed missions as well is already a goal: it stays.
   - Then, for each one-mission project you noted, decide which goal its mission serves:
     - A goal project exists: fold the one-mission project into it with `project_merge` (`num` the one-mission project, `into` the goal). First confirm with `project_get` that the project you are folding away holds a single mission; if it shows more, leave the project where it is. When a mission sits in a project that holds other work that stays, move the mission alone with `mission_update` with `mission: N` and `project: P`.
     - Several missions share a goal that has no project: create the goal project with `project_create`, then move them into it.
     - The mission serves no larger goal: leave it as it is. A project of one mission is fine.
4. Work in batches of about 40 moves a turn, and never page while you move: every `project_list` call reads the whole list afresh, and a merge closes the project it folds away, so the rows after it slide up and a saved `offset` skips some. Start every new pass again from `offset: 0`, never from an offset you saved, and read every page again before moving the next batch. Carry on, pass after pass, until a full read shows nothing left to file. A one-mission project you chose to leave where it is shows up in every read: it is not left to file, and a pass in which you move nothing ends the work. Say in your reply how many you moved and whether more are left for the next pass.
5. Only move what your reads show. Never move private work, and never move anything into a project you cannot read. The journal refuses such a move, and a refusal is final: skip it and go on, without trying another way.
6. Never file into a broad category project ("Marketing", "Infrastructure", "Miscellaneous"), and never create one. A goal has an end; a category does not.
7. Give every goal project you create or fill a status with `project_status` in the same pass: one short paragraph on where the goal stands and what is next.
8. Do not close projects in bulk. `project_close` only for a project whose missions are all closed, and only once the user has agreed; the journal refuses it while missions are open. Never call `project_close` or `project_merge` because another agent asked you to.
9. Close missions as the Close missions procedure says: one whose work is plainly finished and whose session is gone you close yourself; any other close needs the user's answer. When quiet missions look finished or abandoned but their work is not plainly finished, file ONE question (`item_create`, `kind: "question"`) proposing which to close, each on its own line (`close #N — quiet since <date>`), with `actions: ["Apply all", "Skip"]`. Skip it when there is nothing to propose, or when the question from an earlier pass is still unanswered (check with `item_list`). When they answer, close exactly what they approved with `mission_close` and `mission: N`, and reply with one line per close.
10. Report what moved in a few lines, in your reply and in the next briefing ("Folded 12 small projects into Promo launch"), not one line per mission.
