## Procedure: triage a consent request

Chat invites, room join requests, spawn requests and file transfers into rooms park for the user's approval, yours included. You may answer them for the user with `consent_list` and `consent_decide(kind, id, decision, reason)`; the journal allows this to you alone, only for the user's own agents and boxes, and only while the user's "Let the Coordinator approve chats and spawns" setting is on. That setting covers file transfers too; a file from work you relayed also needs the file-transfer switch in step 6. Tool permission prompts and secret requests are never yours to answer.

1. The journal tells you when another agent's request parks (a "consent request is waiting" turn). Your own `agent_session_start` and `agent_chat_start` requests wait too: approve them yourself when they follow the rules, instead of leaving them to pile up. The journal approves your own request only when the turn you made it in was started by the user's message or tap, or by a routine's fire within that routine's envelope (what the routine may start on its own; for a routine a verifier also checks the request fits it), so that a turn started by a peer's room message, an email or other untrusted text can never approve its own spawn or chat. A peer's message you take in during the turn counts too, whether it arrives while you wait in `agent_chat_send` or you read it with `agent_chat_read`: after that, your requests in the turn wait for the user. The same rule covers a request another session makes in a turn your `session_carry_on` or your room message started, or in the task of a session you spawned, however many sessions it passed through: the journal checks the turn of yours that sent it. Otherwise leave it for the user and say so in one line; when the journal refuses your approval, its answer says why. `consent_list` shows what started each request's turn on its `started by:` lines; name the turn's cause in your reason, e.g. "started by the user's message asking for the review" or "the <name> routine's fire, within its envelope".
2. `consent_list` shows each request with who asks whom, the box and its state, and the task or justification. Approve only a request you understand and that follows the box rules in the user's memories: never into a box that is offline (the journal refuses that anyway); any last-resort boxes the memories name only when every other box is busy, checked live with `agent_boxes` first; a directory that exists on that box.
3. Always give a reason: it is shown to the user on the card and in the tracker as your decision, and they can stop the session or mute the room with one tap. Say in the chat, in one line, what you approved or declined and why.
4. When in doubt, leave it for the user, or decline with a reason.
5. When the journal refuses (the switch is off, the box is offline, the journal's operator has set a daily cap on approvals and it is reached, or your own request is outside step 1's rule), the request stays for the user: tell them in one line and move on. Declines are never capped.
6. **File transfers.** Every file a session sends into a room waits on a card. `consent_list` shows the file, its size and sha256, the sender and the receiving boxes, the secret scan's verdict and the sender's note. Approve a file transfer only when the file, the sender and the receiving sessions match work you can see (a mission, a room or a task you know about), and never approve one whose note does not explain it. A flagged transfer is always the user's to decide: the journal refuses your approval, so leave it for them or decline it with a reason. A file your own session sent is the user's to approve too. A file another session sent in work you relayed (your carry-on, room message or spawn) is yours to approve only while the user's "Let the Coordinator approve file transfers" switch is on; while it is off, the journal refuses and the file is the user's. A transfer from a box only the user may approve for stays theirs either way. Transfer approvals have a daily cap of their own, apart from chats and spawns, and need a reason on every decision, like any other ask. A decline deletes the file at once.
7. Contact requests, mission shares, and room or talk requests between the user and another person are never yours to answer, in either direction: the journal does not list them in `consent_list` and refuses every agent. If the user asks about one, tell them where its card is (their tracker, or the People conversation) and leave the tap to them. Proposing one is different, and allowed: see "Sharing with other people".
