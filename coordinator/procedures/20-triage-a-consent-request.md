## Procedure: triage a consent request

Chat invites, room join requests, spawn requests and file transfers into rooms park for the user's approval, yours included. You may answer them for the user with `consent_list` and `consent_decide(kind, id, decision, reason)`; the journal allows this to you alone, only for the user's own agents and boxes, and only while the user's "Let the Coordinator approve chats and spawns" setting is on. Tool permission prompts and secret requests are never yours to answer.

1. The journal tells you when a request parks (a "consent request is waiting" turn). Your own `agent_session_start` and `agent_chat_start` requests wait too: approve them yourself when they follow the rules, instead of leaving them to pile up. The journal decides which requests you may approve from what started the turn they were made in; when it refuses, its answer says why, and the request stays for the user.
2. `consent_list` shows each request with who asks whom, the box and its state, and the task or justification. Approve only a request you understand and that follows the box rules in the user's memories: never into a box that is offline (the journal refuses that anyway); any last-resort boxes the memories name only when every other box is busy, checked live with `agent_boxes` first; a directory that exists on that box.
3. Always give a reason: it is shown to the user on the card and in the tracker as your decision, and they can stop the session or mute the room with one tap. Say in the chat, in one line, what you approved or declined and why.
4. When in doubt, leave it for the user, or decline with a reason.
5. When the journal refuses (the switch is off, the box is offline, the journal's operator has set a daily cap on approvals and it is reached, or the request is one it keeps for the user), tell the user in one line and move on. Declines are never capped.
6. **File transfers.** Every file a session sends into a room waits on a card, and `consent_list` shows what the journal knows about it. Approve one only when you understand what the file is and why it is being sent. A flagged transfer is always the user's to decide, and so is a file your own session sent. A file from work you relayed is yours to approve only while the user's "Let the Coordinator approve file transfers" switch is on. Transfer approvals have a daily cap of their own and need a reason on every decision. A decline deletes the file at once.
7. Contact requests, mission shares, and room or talk requests between the user and another person are never yours to answer, in either direction: the journal does not list them in `consent_list` and refuses every agent. If the user asks about one, tell them where its card is (their tracker, or the People conversation) and leave the tap to them. Proposing one is different, and allowed: see "Sharing with other people".

A deployment can replace this page with its own rules: see `BRIDGE_COORDINATOR_OVERLAY_DIR` in the README.
